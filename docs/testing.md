# Running the tests

| Command | What it runs | Needs |
|---|---|---|
| `npm test` | 192 unit, property and fuzz tests (about 15 seconds; the first PDF test loads a PDF library) | Node only |
| `FUZZ_ITERATIONS=30000 npm test` | the same, with the fuzz tests 20 times deeper (about 30 seconds more) | Node only |
| `npm run test:emulator` | 29 tests against the Firestore, Realtime Database, Auth and Storage emulators | Java 21 on the path (on this machine: `C:\Users\mbanw\tools\jdk-21.0.12.1+1\bin`); no real Firebase project is touched |
| `npm run test:browser` | 9 end-to-end tests of `/packs` in a real Chrome or Edge, against a local copy of the app in LAB mode (takes about a minute: it starts the app) | Google Chrome or Microsoft Edge installed; `playwright-core` (dev dependency) |

## What the fuzz tests do
Seeded random inputs, so a failure prints its seed and iteration and can be repeated. They check that amounts and dates round-trip in every format they generate, that no input makes the statement parser crash or produce an invalid transaction, that a pack's hash is stable and changes when the data does, that the proposed journal always adds up, and that text from a bank can never start a spreadsheet formula in the exported files. I checked they can fail: breaking the trailing-minus rule and breaking the formula guard each made them fail.

## What the browser test does
It creates a pack from a statement, checks the issues list and questions, saves an owner's answer, corrects a category and reloads to see it came back from storage, downloads the journal, edits account numbers (a clashing number is refused), checks every control has a name, checks there is no sideways scrolling at phone width, and erases the company's data (typing the ID is required). It also fails on any script or console error.

## What the newer tests do (2026-10-31)
- `malware-scan.test.ts`: the clamd protocol against a stand-in server that speaks it, the built-in checks, and that an unreachable scanner never clears a file.
- `pdf-text.test.ts`, `receipt-extract.test.ts`: PDFs generated by `tests/fixtures/make-pdf.ts` (text placed in table columns), read by the real PDF library. These are synthetic, not real bank PDFs.
- `vat-and-jurisdictions.test.ts`: sales VAT, the VAT worksheet, country rates and the journal split.
- `xero-connector.test.ts`: the whole Xero flow against a mock of Xero. The real Xero was never called.
- `partner-layer.test.ts`: invitations, plan limits, usage, branding, calendar, exception queue, workload.
- `tests/emulator/partner-and-connections.emulator.ts`: the partner and connection stores on Firestore.

## What none of this covers
Real bank files and real bank PDFs, real Firebase (sign-in, rules, TTL, indexes), the real Xero, a real ClamAV, the Tesseract program, receipt uploads in the browser, the partner pages in a browser (they need real-data mode and a signed-in firm), a screen reader, a real phone, real-data mode.

## Ledger adapters (2026-10-31, second pass)
`ledger-adapters.test.ts` (13 tests): money and date parsing, SmartAccounts timestamp (winter and summer), signature rule recomputed independently, paging and read-only requests against a stand-in, the secret never in a URL or error, request budget leaving a gap, the review's rules and its refusal to say "correct", activation counting (same company twice is one account), partner codes and signed tokens, Xero and QuickBooks mappers against stand-ins, the DATEV pairing. None of this touches a real accounting system; the Firestore activation store has no emulator test yet.

## US systems (2026-10-31, third pass)
`us-systems.test.ts` (7 tests): the shared sign-in for QuickBooks, FreshBooks and Zoho against stand-ins (tokens sealed at rest, state not reusable across providers or users and expiring, more than one business refused, refresh with rotating and non-rotating refresh tokens), provider statuses, and the FreshBooks and Zoho readers (paging, period filter, read-only requests, headers). No real service was contacted.
